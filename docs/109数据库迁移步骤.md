# 109 数据库整库迁移步骤（迁到 Windows + Docker Desktop，不停机）

> 思路：109 不停机，把 PostgreSQL 实例**按文件原样**拷到 Windows 上，在新库上排查损坏，109 原数据不动。
> 用 PostgreSQL 自带的在线备份接口（`pg_backup_start` / `pg_backup_stop`）保证拷出来的数据一致。
> 排查、清理完成后再决定切换方式（另行补充）。

|---|---|

**镜像必须用上面这个 digest**：保证 PG 小版本、PostGIS/pgRouting 版本、glibc 排序规则与 109 完全一致，否则文本索引可能失效。

### 为什么不能只 rsync 一遍就用

库在运行时，哪怕写得很少，也会有数据页、事务状态文件（`pg_xact`）、控制文件在拷贝过程中被改，拷出来的各个文件不在同一时间点。这样的副本可能起不来，也可能出现"拷贝造成的假损坏"，和 109 上真正的损坏混在一起，排查时分不清。

在线备份接口解决的就是这个问题：开始时记下一个检查点，结束时记下终点，新库启动时自动用这段 WAL 把所有文件补齐到同一时间点。**109 全程正常服务，不改配置、不重启。**

## 第 0 步：Windows 准备（不影响 109）

> 文中 Windows 命令在 cmd 和 PowerShell 里都能直接运行（外层统一用双引号）。

1. **Docker Desktop 设置**
   - 使用 WSL 2 后端（默认）。
   - Settings → Resources → Advanced → **Disk image location** 放到空间充足的盘（至少 600 GB 可用）。
     Docker 的卷都在这个虚拟磁盘里。**PG 数据不要用绑定挂载放到 NTFS 目录（如 `D:\pgdata`）**，权限和 fsync 都有问题，只用 Docker 命名卷。
   - 内存：在 `%UserProfile%\.wslconfig` 写入下面内容，然后在 PowerShell 执行 `wsl --shutdown` 并重启 Docker Desktop：
     ```ini
     [wsl2]
     memory=24GB
     ```
     数值按 Windows 机器实际内存调整，建议给到一半左右。

2. **拉镜像并建卷**（PowerShell）
   ```powershell
   docker pull docker.io/pgrouting/pgrouting@sha256:5e6767abbd1fd9ead84c9988aa31bac71ca292ef8a1fc2e4a5ee2b613ac6a7bb
   docker volume create pg109_data
   docker volume create pg109_ssh
   ```

3. **生成拷贝用的 ssh 密钥**
   ```powershell
   docker run --rm -it -v pg109_ssh:/root/.ssh alpine:3.20 sh -c "apk add --no-cache openssh-client && ssh-keygen -t ed25519 -N '' -C pg109-migrate -f /root/.ssh/id_ed25519 && cat /root/.ssh/id_ed25519.pub"
   ```
   把输出的公钥加到 109 的 `/root/.ssh/authorized_keys`。迁移结束后删掉这一行。

4. **测试连通**
   ```powershell
   docker run --rm -it -v pg109_ssh:/root/.ssh alpine:3.20 sh -c "apk add --no-cache openssh-client && ssh -o StrictHostKeyChecking=accept-new root@10.255.254.109 'du -sh /data3/kube-deploy-data/pgrouting'"
   ```

## 第 1 步：在线预拷贝大头（约 35–50 分钟）

先把 197 GB 拷过来。这一份不一致，**不能启动**，第 2 步会把它补成一致的。

- 中途断了直接重跑同一条命令，会接着传。

## 第 2 步：在线备份补齐（不停机，约 5–10 分钟）

> **简化路线（实际采用）**：109 上除 seata / nacos / i18n / workflow 几个小库外基本只读，只要求每个库、每张表的数据都在，可以跳过第 2 步，直接按第 3 步启动，由 PG 自动做崩溃恢复。
> - 启动失败并报 `could not locate a valid checkpoint record` 时，可在副本上用 `pg_resetwal -f` 强制启动（只影响副本）。
> - 有写入的那几个小库可能不是最新的，需要时从 109 用 `pg_dump` 单独重新导一份。
> - 启动后用 `pg_class.reltuples` 对比两边每张表的行数估算值，不在 109 上做全表扫描，避免读到坏块把 109 弄崩。

在 Windows 上开**两个 PowerShell 窗口**，按顺序操作。

**窗口 A：连上 109，开始备份**

用镜像里自带的 psql 连 109，同时把数据卷挂进来，方便最后直接写文件：

```powershell
docker run --rm -it -v pg109_data:/data docker.io/pgrouting/pgrouting@sha256:5e6767abbd1fd9ead84c9988aa31bac71ca292ef8a1fc2e4a5ee2b613ac6a7bb psql -h 10.255.254.109 -p 5443 -U postgres -d postgres
```

输入 109 的 postgres 密码后执行：

```sql
SELECT pg_backup_start('win-migrate', true);
```

返回一个 LSN（形如 `4A/1B000028`）即表示开始。`true` 表示立即做一次检查点，库基本只读，开销很小。

> **这个 psql 窗口在第 2 步结束前不能关、不能断。** 会话一断，这次备份就作废。

**窗口 B：补齐差异**

```powershell
docker run --rm -it -v pg109_data:/data -v pg109_ssh:/root/.ssh alpine:3.20 sh -c "apk add --no-cache rsync openssh-client && rsync -aH --numeric-ids --info=progress2 --delete --checksum --exclude=postmaster.pid --exclude=postmaster.opts root@10.255.254.109:/data3/kube-deploy-data/pgrouting/ /data/"
```

`--checksum` 会把两边文件都完整读一遍再比对，确保不漏掉任何改动，耗时主要在读盘（197 GB，NVMe 上几分钟）。

**窗口 A：结束备份，写入备份标记文件**

窗口 B 的 rsync 完成后，回到窗口 A 依次执行：

```
\pset tuples_only on
\pset format unaligned
SELECT labelfile FROM pg_backup_stop(false) \g /data/backup_label
\q
```

这一步把备份的起点信息写进新库数据目录下的 `backup_label`。新库启动时靠它知道从哪里开始补 WAL。

**窗口 B：补最后一段 WAL，并修正标记文件权限**

```powershell
docker run --rm -it -v pg109_data:/data -v pg109_ssh:/root/.ssh alpine:3.20 sh -c "apk add --no-cache rsync openssh-client && rsync -a --numeric-ids --checksum --info=progress2 root@10.255.254.109:/data3/kube-deploy-data/pgrouting/pg_wal/ /data/pg_wal/ && chown 999:999 /data/backup_label && chmod 600 /data/backup_label && cat /data/backup_label"
```

最后打印出的 `backup_label` 应包含 `START WAL LOCATION`、`CHECKPOINT LOCATION`、`BACKUP METHOD: streamed`、`LABEL: win-migrate` 等几行。

### 第 2 步注意事项

- **顺序不能乱**：先 `pg_backup_start`，再 rsync，再 `pg_backup_stop`，再补 WAL。`backup_label` 必须在带 `--delete` 的那次 rsync **之后**写入，否则会被删掉。
- **如果 109 在这几分钟内崩了**（窗口 A 报连接断开，或 `pg_backup_stop` 报 `backup is not in progress`）：这次作废，从窗口 A 的 `pg_backup_start` 重新开始。数据大头已经在 Windows 上，重做一次也只要几分钟。
- **`backup_label` 不存在时绝对不要启动新库**：没有它，PG 会当作普通启动，得到一个不一致但看起来正常的库。
- 备份期间 109 照常读写，用户无感知。

## 第 3 步：在 Windows 上启动新库

新建一个目录（例如 `D:\pg109`），放入 `docker-compose.yml`：

```yaml
services:
  pg109:
    image: docker.io/pgrouting/pgrouting@sha256:5e6767abbd1fd9ead84c9988aa31bac71ca292ef8a1fc2e4a5ee2b613ac6a7bb
    container_name: pg109
    restart: "no"          # 排查阶段崩了不自动拉起，方便看日志
    shm_size: 2g
    ports:
      - "15432:5432"       # 和 109 区分开
    environment:
      PGDATA: /var/lib/postgresql/data
      TZ: Asia/Dubai
    volumes:
      - pg109_data:/var/lib/postgresql/data
    command:
      - postgres
      - -c
      - max_connections=200
      - -c
      - shared_buffers=4GB
      - -c
      - work_mem=32MB
      - -c
      - maintenance_work_mem=1GB
      - -c
      - effective_cache_size=12GB
      - -c
      - timezone=Asia/Dubai
      - -c
      - log_timezone=Asia/Dubai
      - -c
      - log_min_duration_statement=1000
      - -c
      - "log_line_prefix=%m [%p] %d %u@%r "   # 记下库名、用户、来源，排查用

volumes:
  pg109_data:
    external: true
```

```powershell
cd D:\pg109
docker compose up -d
docker logs -f pg109
```

**启动日志里应依次看到：**
1. `starting backup recovery with redo LSN ...`：识别到了备份标记，开始补 WAL。
2. `consistent recovery state reached at ...`：已补到一致状态。
3. `database system is ready to accept connections`：可以使用。

启动成功后 `backup_label` 会被自动改名为 `backup_label.old`。

如果出现 `WAL ends before end of online backup`，说明第 2 步最后那次 WAL 没补全：`docker compose down`，重做第 2 步。

**校验库清单**：

```powershell
docker exec pg109 psql -U postgres -d postgres -Atc "select datname, pg_size_pretty(pg_database_size(datname)) from pg_database where not datistemplate order by 1"
```

与 109 上同样的查询对比，28 个库都在、大小一致（seata / i18n 几个有写入的库可能有极小差异）。

需要别的机器访问时，在 Windows 防火墙放行 15432 入站。用户名密码与 109 相同。

## 第 4 步：在新库上排查损坏

在新库上做，崩了也只影响这台 Windows 上的容器。

```powershell
docker exec pg109 sh -c "pg_amcheck -U postgres --all --install-missing -j 4 --progress > /tmp/amcheck.log 2>&1"
docker cp pg109:/tmp/amcheck.log .\amcheck.log
```

- 如果中途实例崩溃（`docker logs pg109` 里出现 `terminated by signal`），记下当时在查的库和表，`docker start pg109` 后用 `--exclude-relation` 跳过这张表再跑。
- 已知嫌疑最大的库，可以先单独查：
  ```powershell
  docker exec pg109 pg_amcheck -U postgres -d makani_sync_full --install-missing -j 4 --progress
  docker exec pg109 pg_amcheck -U postgres -d makani_1119 --install-missing -j 4 --progress
  ```

排查结果出来后，再决定每张坏表的处理方式，以及最终是原地清理后开启校验，还是逐库导出到一个开启了 `--data-checksums` 的全新实例。
