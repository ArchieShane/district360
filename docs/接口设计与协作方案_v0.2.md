## 2. 总体架构：抽取到统计库，接口只读统计库

### 2.1 为什么要单独的统计库

页面只有区级汇总数（17 区 × 约 30 个字段 + 12 个月度值），没有明细，新原型的设计说明也是这个方案。理由：

1. **运行时只依赖一个库**。查询不再同时连三个源库（ADREC 还在别的实例），哪个源慢了、断了、在重新同步（比如现在 udm_plot 只有 1 万行），页面都显示上次成功抽取的结果。
2. **快且稳定**。接口就是按 code 查几行；不用在源库上加索引（makani_1119 是同步库，我们不维护它的结构）。
3. **协作边界清楚**。各方的交付物是「把自己源的数写进自己那张统计表」，契约就是表结构。
4. **数据日期可追溯**。每行带 `source_as_of`（源数据日期）和 `extracted_at`，页面每个区块标的数据日期就从这里来。

> 单看 makani，直查也不慢（单区 0.4 s）。统计库主要解决多源稳定性和协作问题。

### 2.2 数据流

```
 makani_1119 (ods) ──┐  MakaniExtractor      【我们】
 liveability_...  ───┼─ LiveabilityExtractor 【宜居】     每日定时 + 手动触发
 ADREC (另一实例) ───┘  AdrecExtractor       【房地产】
                          │ 各写各的表（按源整批替换，单事务）
                          ▼
                district360 统计库（schema: stat）
                各源分表 + 视图 v_district_360（= 原型说的 district_360 宽表）
                          │ 只读，MyBatis
                          ▼
                Spring Boot REST /api/v1/**  ──►  Vue3 前端
```

为什么分表再用视图拼，而不是三方写同一张宽表：每个人只 `delete + insert` 自己的表，互不锁、互不覆盖；某个源抽取失败不会把宽表里别人的列清空。

### 2.3 后端模块

```
backend/
├─ d360-common        统一返回体、DTO、StatExtractor 接口、区字典
├─ d360-stat          统计库数据源、Flyway 建表脚本、读统计表的 Mapper     【我们】
├─ d360-makani        makani 数据源 + MakaniExtractor                      【我们】
├─ d360-liveability   Liveability 数据源 + LiveabilityExtractor            【宜居】
├─ d360-adrec         ADREC 数据源 + AdrecExtractor                         【房地产】
└─ d360-app           启动类、Controller、定时调度、抽取日志
```

**多数据源**：统计库是接口唯一的数据源（主数据源）；三个源库只给各自的 Extractor 用。每个源模块单独声明 `DataSource` + `SqlSessionFactory`，按 mapper 包扫描区分，不用动态切换。

```yaml
d360:
  datasource:
    stat:        { url: jdbc:postgresql://<待定>/district360?currentSchema=stat, ... }
    makani:      { url: jdbc:postgresql://10.255.254.109:5443/makani_1119?currentSchema=ods, username: ${MAKANI_DB_USER}, password: ${MAKANI_DB_PASSWORD} }
    liveability: { url: jdbc:postgresql://10.255.254.109:5443/liveability_data_20260730, ... }
    adrec:       { url: <ADREC 同事提供>, ... }
  makani: { schema: ods, table-prefix: ods_makani_ }
  etl:
    enabled: true
    cron: "0 0 3 * * *"
```

单个 Extractor 失败只记日志、不覆盖旧数据，也不影响其他源。

## 3. 统计库表结构（契约）

| 表 | 粒度 | 主要字段 | 写入方 |
|---|---|---|---|
| `dim_district` | 每区一行 | code、name_en、name_ar、page_name、makani_district_id、liv_district_id、sort_no、centroid、bbox、boundary（简化后的多边形） | 我们（区字典 + makani 区面） |
| `stat_district_makani` | 每区一行 | area_km2、communities、plots、buildings、buildings_uc、plots_constructed、plots_uc、plots_vacant_serviced、plots_vacant_unserviced、schools、medical、mosques、source_as_of、extracted_at | 我们 |
| `stat_district_landuse` | 区 × 用地类别 | use_desc（makani 原始用途），归类为 residential / commercial / community / open_space / other、plot_count、pct | 我们 |
| `stat_district_liveability` | 每区一行 | score_existing、score_current（Pipeline）、score_target（AP50）、parks、park_area_ha、park_gap_ha、source_as_of、extracted_at；不在宜居评估范围的区不写行 → 页面显示「未纳入评估」 | 宜居 |
| `map_adrec_community` | ADREC 社区一行 | adrec_community_name、district_code（null = 未映射）、remark | 房地产 |
| `stat_district_adrec` | 每区一行 | period_start_month、period_end_month、sales_aed、sales_yoy_pct、tx_count、mortgage_count、avg_price_sqm、active_leases、source_as_of、extracted_at | 房地产 |
| `stat_district_adrec_monthly` | 区 × 月 | month、tx_count（12 柱） | 房地产 |
| `map_building` | 每栋建筑 | district_code、building_id、height、geom（只存 17 区，约 2.2 万栋） | 我们 |
| `etl_job_log` | 每次抽取 | source、started_at、finished_at、status、row_count、message | 框架自动写 |
| `v_district_360`（视图） | 每区一行 | 上面各表按 code 左连接 | 我们 |

- 人口字段**不建**（新原型明确不写入页面数据）。
- 建表脚本用 Flyway 管理，放 `d360-stat`，**由我们统一维护**；同事要加字段提 PR。
- 抽取接口：

```java
public interface StatExtractor {
    String source();                                       // makani / liveability / adrec
    ExtractResult extract(List<DistrictRef> districts);    // 读源库 → 整批替换自己的统计表
}
```

`DistrictRef` 同时带 code、makani 区 ID / 区面、liv id，各方用自己需要的。

- **开发期种子数据**：dev 环境的 Flyway 用原型内嵌的 17 区样例数填充所有统计表，第一天前端就能跑通整页；哪个源的 Extractor 写好了，跑一次就覆盖成真实数据。

## 5. 区列表（以数据库为准）

- 来源：makani `udm_district` 中的全部区（216 个：ADM 101、AAM 69、WRM 46），按区名排序，由 makani 抽取写入 `stat.dim_district`（区名、阿拉伯文名、区面、统计范围、中心点、外包框）。
- 区编码：市政 + 区名，`ADM` + `AL REEM ISLAND` → `adm-al-reem-island`（AL BATEEN、AL RAWDAH 在 ADM 和 AAM 都有，所以必须带市政）；显示名为首字母大写形式；makani 内部用 objectid 作为区的唯一键。
- 不再维护配置清单，也就不存在「区对应关系待确认」：原型里的 Al Wahda 在数据库中不存在，自然不在列表里；Al Mina 即 Zayed Port，Saadiyat 即 Al Saadiyat Island，Hudayriyat 即 Al Hidayriyyat。
- 宜居 / ADREC 不需要区对应表：按统计范围（makani 区面）做空间查询。已验证 Liveability 区面与 makani 重合（IoU ≥ 0.997）；Liveability 同样有 216 个区。
- 接口：`GET /api/v1/districts?page&size&q` 分页（左侧列表滚动加载）；地图边界与标签一次性加载全部区。

## 6. 协作方式

| 角色 | 交付 |
|---|---|
| 我们 | 仓库骨架；d360-common / d360-stat（Flyway 建表 + 种子数据）/ d360-app；区字典；MakaniExtractor（含区面、建筑）；6 个接口；前端整页 |

规则：
1. 统计表结构、DTO、`StatExtractor` 接口只由我们改；改动走 PR，三方 review。
2. 每人一个模块目录，分支 `feature/liveability-*`、`feature/adrec-*`，PR 到 `main`。
3. 验收方式：跑一次 `POST /api/v1/admin/etl/{source}`，`etl_job_log` 成功、对应统计表有数据、页面对应区块变成实数。原型约定的验收是「Al Reem 与智能体答案核对，再抽检 2 个区」。
