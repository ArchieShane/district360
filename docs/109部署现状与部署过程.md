## 6. 首次部署过程（完整包）

适用：全新的服务器，或镜像 / 基础环境变化。

### 6.1 出包（开发机）

```bash
deploy/docker/build-package.sh                # 完整包：编译 jar、打包前端、在 BUILD_HOST 上做镜像并导出
SKIP_IMAGE=1 deploy/docker/build-package.sh   # 升级包：只有 jar + 前端
```

- 产物在 `deploy/docker/out/district360-docker-<时间戳>.tar.gz`。
- 脚本默认到 `root@10.255.254.109` 构建镜像（`BUILD_HOST`）。镜像要求 x86_64（构建完会打印架构，确认是 `amd64`）。
- 脚本已自动从 jar 中删除 `application-local.yml`（开发库密码不随包带出）。**出包后检查**：

  ```bash
  unzip -l deploy/docker/out/district360/jar/district360.jar | grep -E 'application-local\.yml$'   # 应无输出
  ```

### 6.2 传包、解压（109）

```bash
scp deploy/docker/out/district360-docker-<时间戳>.tar.gz root@10.255.254.109:/root/
ssh root@10.255.254.109
cd /root && tar xzf district360-docker-<时间戳>.tar.gz --no-same-owner && cd district360
```

> 在 macOS 上打的包，解压到 Linux 时文件属主会变成 uid 501（109 上现状就是）。加 `--no-same-owner`（或解压后 `chown -R root:root .`）可避免。

### 6.3 填配置

```bash
vi config/application-prod.yml   # 把 <...> 占位符全部替换：统计库、makani、宜居、ADREC 四个库的地址和账号
vi .env                          # 一般不用改；端口 D360_HOST_PORT=8360，二级路由 D360_CONTEXT_PATH=/district360
chmod 600 config/application-prod.yml
```

按本文第 3 节的数据源填写。`start.sh` 会检查是否还有 `<...>` 占位符，没填好会拒绝启动。

统计库首次使用前，先在库里建库并装 PostGIS（表由程序启动时自动建）：

```sql
CREATE DATABASE district360;
-- 在 district360 库里：
CREATE EXTENSION IF NOT EXISTS postgis;
```

### 6.4 启动与验证

```bash
./start.sh                                    # 导入镜像 + 启动容器
docker ps --filter name=district360           # 约 1 分钟后 STATUS 显示 (healthy)
curl -s http://127.0.0.1:8360/district360/api/v1/meta
./start.sh logs                               # 或 tail -f logs/district360.log
```

统计表为空时，程序启动后会在后台自动跑一次 makani 抽取（约 2.5 分钟）。日志里应看到 `Started District360Application`。

## 7. 日常升级过程（升级包）

**升级包只含 `jar/` 和 `static/`，不会覆盖 `config/` 和 `.env`。** 每次升级都要有一份升级说明（模板见 [releases/升级说明-20261123.md](releases/升级说明-20261123.md)），内容固定为：本次改了什么、是否含数据库迁移（V 号）、是否需要核对源库字段、是否需要重新抽取、验证方法、回滚方法。

### 第 0 步：确认包完整

```bash
sha256sum district360-upgrade-<版本>-<日期>.tar.gz     # 与升级说明里的 SHA-256 一致才继续
```

### 第 1 步：检查 makani 源库字段（新版多读源字段时必做）

在 **makani 源库**（111 上 `makani_sync_full`）执行 [deploy/docker/check-makani-columns.sql](../deploy/docker/check-makani-columns.sql)（只读）。文件开头 `params` 的 `schema` / `table-prefix` 与 `config/application-prod.yml` 保持一致（111 全量库：`public` 和空串）。**结果为空才继续**，有结果先不要升级，发给开发。

### 第 2 步：备份当前版本（统一命名：`.bak-<日期>`）

在 `/root/district360` 下：

```bash
D=$(date +%Y%m%d)
cp -p jar/district360.jar jar/district360.jar.bak-$D
cp -a static static.bak-$D
cp -p config/application-prod.yml config/application-prod.yml.bak-$D   # 只有改配置时才需要
```

### 第 3 步：替换并重启

```bash
mkdir -p /tmp/d360-up && tar xzf <升级包路径> -C /tmp/d360-up --no-same-owner
cp /tmp/d360-up/district360/jar/district360.jar jar/district360.jar
find static -mindepth 1 -delete && cp -R /tmp/d360-up/district360/static/. static/
docker restart district360
```

### 第 4 步：确认启动成功

```bash
./start.sh logs        # Ctrl+C 退出
```

日志应有：

- 含迁移时：`Successfully applied N migration to schema "stat", now at version vX`
- `Started District360Application`

约 1 分钟后 `docker ps --filter name=district360` 显示 `(healthy)`。

### 第 5 步：需要时重新抽取

迁移只加列、不清表时，已有数据的新字段是空的，要手动触发一次抽取，或等次日 03:00：

```bash
curl -m 900 -X POST -H "X-Admin-Token: <口令>" http://127.0.0.1:8360/district360/api/v1/admin/etl/makani
# 也可以 /etl/all；约 1.5~2.5 分钟返回，"status":"success" 为成功
```

### 第 6 步：验证

```bash
curl -s http://127.0.0.1:8360/district360/api/v1/meta     # 三个源 lastStatus=success，lastFinishedAt 为刚才的时间
```

打开页面选中一个区：地图出边界、右侧面板有数、悬浮能看到指标来源；按本次升级内容再点检新功能。

### 回滚

```bash
cp -p jar/district360.jar.bak-<日期> jar/district360.jar
find static -mindepth 1 -delete && cp -R static.bak-<日期>/. static/
docker restart district360
```

- 统计库**不用回滚**：旧版程序不读新增的列，Flyway 也会忽略比自己新的迁移记录（仅限"只加列"的迁移；若迁移改了表结构或删了东西，回滚前先备份统计库）。
- 只改配置：恢复 `config/application-prod.yml.bak-<日期>` 后 `docker restart district360`。

## 9. 对照交接规范发现的问题（109 上实际情况）

| # | 现象 | 影响 | 建议 |
|---|---|---|---|
| 1 | **线上 jar 与本地升级包对不上**：109 的 jar 与 `district360-upgrade-202611231449.tar.gz` 里的 jar 大小一致（27,670,608 字节），但 SHA-256 不同（线上 `05f45cd9…`，包内 `5c81d331…`）。多半是同一份代码重新构建了一次，但目前**无法证实**线上跑的是哪个 commit | 出问题时不知道线上是哪版代码 | 落实 [交接与规范](交接与规范.md) 第 5.2 节：包内带 `VERSION`（含 commit）和 `SHA256SUMS`；部署时记录线上 jar 的 SHA-256 |

| 3 | 备份文件命名不统一：`district360.jar.bak`、`district360.jar.bak-20261123`（实际是 11-21 的版本）、`static.bak-20261123` | 分不清哪个是哪次升级前的 | 统一用 `.bak-<升级当天日期>`，并在升级说明里记下 |
| 4 | 备份文件没有清理策略 | 长期占磁盘 | 保留最近两次备份，更早的删除 |
| 5 | `logs/etl-all-result.json` 是 11-21 手动触发的遗留文件 | 无害 | 可删；手动抽取结果不要落在部署目录里 |
| 6 | 没有反向代理，直接访问 `10.255.254.109:8360` | 若要对外用域名访问，需另配 Nginx | 配置示例见 [deploy/docker/README.md](../deploy/docker/README.md) 的 Nginx 一节；注意 `proxy_pass` 不要去掉 `/district360` 前缀 |
| 7 | 构建镜像和运行服务都在 109 | 109 是共用服务器且有硬件问题，构建机不稳定 | 评估是否把构建机换成独立机器；运行侧后续是否迁出 109 也一并考虑 |
| 8 | `Broken pipe` 异常按 ERROR 级别记 | 日志噪音，容易盖住真正的错误 | 开发侧在 `GlobalExceptionHandler` 里对 `AsyncRequestNotUsableException` 降级 |
